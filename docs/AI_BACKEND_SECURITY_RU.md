# Kolzai — подключение языковой модели без утечки ключей

## Текущее состояние
Android-чат сохраняет текущие сообщения в состоянии интерфейса. Добавлен HTTPS-only клиент для `POST /v1/chat`: при заданном `CHAT_BACKEND_URL` он отправляет текст и `conversationId`, проверяет размер запроса и ответа, отключает автоматические HTTP-перенаправления и показывает отдельные ошибки авторизации, лимитов и недоступности модели. Если URL не задан, приложение продолжает работать в автономном режиме через локальную базу.

Серверный endpoint, постоянное хранение истории, потоковая выдача и механизм входа пока не реализованы. Клиент принимает короткоживущий токен через runtime-поставщик, но сам поставщик авторизации ещё не подключён. Поэтому наличие URL само по себе не означает, что чат уже работает: backend должен существовать, проверять авторизацию и поддерживать описанный ниже контракт. RobloxKnowledge.kt содержит локальные справочные материалы, но сам по себе не генерирует ответы.

Для локальной конфигурации можно передать Gradle-свойство `-PCHAT_BACKEND_URL=https://api.example.com`. URL должен быть origin без пути, query или fragment. Не записывай токены и ключи в Gradle-свойства, BuildConfig или Git.

## Целевая схема
Android app → HTTPS API Kolzai → серверный обработчик → провайдер модели → ответ Android app.

Мобильное приложение не должно обращаться к провайдеру с постоянным секретным ключом, встроенным в APK.

## Защита секретов
- API-ключ хранится только в переменной окружения/секретах серверного хостинга.
- Не добавляй ключ в Kotlin, Gradle, AndroidManifest, GitHub, ZIP-архив проекта или логи.
- Не используй BuildConfig для постоянного приватного ключа: значения APK можно извлечь.
- Если ключ случайно попал в репозиторий, считай его скомпрометированным: отзови и выпусти новый.
- Android-клиент использует HTTPS и собственную авторизацию/лимиты сервера.
- Не доверяй userId, лимитам и ролям, присланным клиентом без серверной проверки.

## Контракт API (предлагаемый)
POST /v1/chat
Content-Type: application/json
Authorization: Bearer <короткоживущий токен приложения>

Тело:
{
  "message": "Пользовательский запрос",
  "conversationId": "идентификатор диалога",
  "mode": "roblox"
}

Успешный ответ:
{
  "reply": "Ответ помощника",
  "conversationId": "идентификатор диалога"
}

Ошибки:
- 400: некорректное тело или слишком длинный запрос.
- 401/403: отсутствует или недействительна авторизация.
- 429: превышен лимит запросов.
- 502/503: провайдер модели временно недоступен.
- 500: внутренняя ошибка без раскрытия секретов и stack trace клиенту.

Это проектный контракт, а не уже работающий endpoint.

## Серверная логика
1. Проверить авторизацию, размер запроса и rate limit.
2. Ограничить размер истории диалога и число токенов.
3. Добавить RobloxKnowledge.systemGuidanceRu() и релевантные уроки как контекст.
4. Передать запрос провайдеру модели с ключом из серверной среды.
5. Проверить и нормализовать ответ.
6. Вернуть ответ без секретов, внутренних логов и скрытых рассуждений.
7. Записать безопасную телеметрию: время ответа, код статуса, расход; не логировать ключи и чувствительные пользовательские данные.

## Критерии готовности
- [ ] Серверный endpoint развернут по HTTPS.
- [ ] Ключ провайдера хранится только в секретах хостинга.
- [ ] Есть лимит длины сообщений и частоты запросов.
- [ ] Ошибки провайдера корректно обрабатываются.
- [ ] История диалога ограничена.
- [ ] Android-клиент показывает состояния загрузки и ошибки.
- [ ] Протестированы успешный ответ, неверная авторизация, лимит и недоступность модели.

## Важное
Не считать интеграцию завершённой по наличию этого документа. Для реальной работы нужны серверный код, развертывание, секрет провайдера и подключение Android-клиента.
